# 最小可运行演示：自然语言 → 参数化模型 → 本机真实求解

## 交付范围

这是V0.5的附加启动方式，保留原九个主模块。运行“启动完整示例.bat”后，在工作台点击“打开四节点贯通示例”。原“启动平台.bat”仍运行不含真实求解的V0.5。

本例是明确限定的四节点无损运输网络MILP：大模型API负责读取自然语言、提取数值、识别模板适用性；人工确认；后端从受控模板编译数学模型并调用SciPy/HiGHS。它不是任意生成代码执行器，不代表大理905节点AC-OTS或ProOPF四级题目都已经求解。

参考题来自铮昊demo_4.py（原稿仍在reference/zhenghao）。为使原题可计算，本示例明确补充：调度1小时；线路固定连接费在本时段按投运线路计一次；忽略损耗；只使用节点平衡与线路容量；不加入相角、电压、无功、N−1或弃负荷。这些是新增演示约定，不是原稿暗含的条件。原ProOPF题库未修改。

## 你需要准备

- 主模型API：基础地址、模型标识、Chat Completions兼容路径、密钥。密钥只填界面，不发到聊天、不放文档。
- Python与NumPy/SciPy：已在用户电脑默认Python 3.11.9中探测并实际运行，SciPy版本1.17.1。该环境无需另外安装求解器。
- 在另一台电脑运行时，需Python 3.10+、支持scipy.optimize.milp的SciPy及NumPy；测试脚本的Playwright仅开发验证用，运行网页不需要。
- 无需模型权重、GPU或云求解器密钥；无需先接课题2、课题3或全量大理数据。

## 启动

1. 解压完整项目到独立目录。
2. 双击 `启动完整示例.bat`；或运行 `python serve_demo.py`。
3. 浏览器打开 `http://127.0.0.1:8766`。程序仅监听本机回环，不开放公网端口。
4. 端口占用时：`python serve_demo.py --port 8770`。
5. 配置模型API请到“数据与模型 → 模型／课题接口 → 通用建模模型”，保存并测试。

网页API地址配置保存在浏览器同源存储，8766与原8765端口的配置不共用；新入口需要重新填写。密钥刷新后需重新填写。默认网关只转发公共HTTPS；只对已经信任的内网服务使用 `--allow-private-api`，不是部署本地模型。

## 路线A：不填API，先确认计算链可运行

工作台 → 打开四节点贯通示例 → 需求理解 → 载入已核定数值（不调用LLM） → 动态建模：核对数值表 → 校验参数并编译数学模型 → 数学模型：确认此版数学模型 → 模型校验：进入优化求解 → 运行本机真实求解 → 结果分析 → 导出本次输入、模型与结果。

这条路径明确标记未调用LLM，但最后是实际执行优化计算，不读取预存最优值。

## 路线B：填API，验证真实自然语言入口

步骤与A相同，但需求页使用“调用模型API解析”，而不是“载入已核定数值”。

一次请求要求模型返回executable_spec、missing_information、unsupported_requirements和mapping_evidence。没有实际API密钥时，不能把此链路称为已用真实LLM跑通。网络联通也不保证模型每次理解、字段或数值都正确，仍需人工核对。

模型只得到中文题干、接口Schema和规则，不得到本次预期最优值。模型返回的数值由后端严格校验；执行未知的物理约束类型会被拒绝，不能默默忽略。输出方程由白名单模板编译，保证实际求解使用的数学结构与此模板一致，不宣称是在运行任意LLM生成代码。

## 基准题完整中文需求

见根目录“完整中文需求.txt”。网页也内置同一原文。参数表：

| 项目 | 数值 |
|---|---|
| 时长 | 1小时 |
| G1 / 节点1 | 0～100 MW，300元/MWh |
| G2 / 节点2 | 0～100 MW，500元/MWh |
| 节点3、4负荷 | 50、100 MW |
| 线路顺序 | (1,2)、(1,4)、(2,3)、(2,4)、(3,4) |
| 容量 MW | 50、50、100、100、100 |
| 固定成本 元/时段 | 50、50、50、150、50 |

实际目标函数：

min 300 P_G1 + 500 P_G2 + 50 z_L12 + 50 z_L14 + 50 z_L23 + 150 z_L24 + 50 z_L34

节点平衡（线路按from→to为正方向）：

P_G1 − f_L12 − f_L14 = 0
P_G2 + f_L12 − f_L23 − f_L24 = 0
f_L23 − f_L34 = 50
f_L14 + f_L24 + f_L34 = 100

机组按各自上下限；每条线路 −capacity*z ≤ f ≤ capacity*z，z为0/1。求解程序返回后独立重算功率平衡、出力边界、线路容量、开关整数性与费用；这不是AC电力物理或N−1验证。

## 已实算的结果与修改演示

| 情形 | 结果 |
|---|---|
| 基准题 | 55,200元；G1=100 MW，G2=50 MW；L24断开，其他投运 |
| 节点4负荷改80 MW | 45,200元；G1=100 MW，G2=30 MW |
| 基准题的L23容量改80 MW | 55,300元；L24投运、L34断开；机组仍为100/50 MW |
| 节点4负荷改250 MW | 不可行；不显示旧解或假目标值 |

上表是测试基准，不写进求解算法作为返回答案。每次点击计算都会从当前规格重新建模求解，带新run_id与规格SHA256。

其中基准题线路流为L12=50、L14=50、L23=100、L24=0、L34=50 MW。实际机组成本55,000元，线路费用200元。

## API分工

- 已有 `/api/proxy`：网页网关转发实际模型API。
- 新增 `GET /api/demo/info`：读取中文题、参数契约与参考输入，不含预期最优值。
- 新增 `POST /api/demo/compile`：输入 `{spec: ...}`，输出规范化规格、SHA256、变量、目标、约束。
- 新增 `POST /api/demo/solve`：输入 `{spec: ..., expected_spec_sha256: ...}`，执行当前规格的真实计算并回传结果。仅本机，有会话令牌，限一个并行任务，每次限10秒。
- 一般大理求解程序尚未封装成业务API，不能把这个受限示例端点当作通用AC-OTS服务。

大理程序后续建议另设POST /api/solver/jobs、GET /api/solver/jobs/{id}等任务接口；此处是设计建议，未宣称已实现。优先包装已有能运行的程序，不直接执行未知模型生成的代码。
